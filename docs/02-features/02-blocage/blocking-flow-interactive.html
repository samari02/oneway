Post-mortem

Pourquoi missav123.jp / .com passait

Quatre points de rupture en chaîne — détecté ≠ bloqué à l’écran.

1 · DNR

Miss sur les mirrors numérotés

rules.json contient missav.com, .ws, .app… mais pas missav123.jp ni missav123.com. Chrome laisse la requête partir.

public/rules.json

2 · Domain heuristic

Détecté via « missav »

DOMAIN_ADULT_PATTERNS match missav dans le hostname → score +80 → isExplicit: true. Clarity sait que c’est adulte.

page-analyzer.ts · analyzeDomainName

3 · Keywords JP

\b casse le matching CJK

Des mots comme エロ, 人妻, フェラ sont sur la page, mais \b (word boundary ASCII) ne s’applique pas au japonais. Le filet HTML textuel ne renforce pas le signal.

page-analyzer.ts · keywordMatchesInText

4 · Service worker

isExplicit sans redirect

Dans handlePageAnalysisResult, si result.isExplicit : action = 'block' puis return — sans chrome.tabs.update vers le block-screen. La branche score, elle, redirige.

service-worker.ts · lignes ~560–563

Suite stratégique — boucle auto-améliorante

Organising principle · ordre contraint

Le produit ne « ajoute plus de mots ». Il observe les blocs et la structure des pages, propose des domaines candidats, les promeut dans une liste sync, les passe par une porte d’éval, puis les déploie dans l’extension — en boucle.

Boucle · step through 1 / 5 — Observe
→ → → →

Observe — blocs + signaux structurels

Ce qu’on voit déjà : redirects monk, hits DNR, et surtout la structure de page (meta RTA, age-gate, player + grille de thumbs) — pas la langue des mots-clés.

  • Priorité : signaux structurels ≫ listes lexicales multilangues
  • Chaque block / near-miss alimente la boucle, pas seulement un log
  • Hostname neutre + page « adult-shaped » = signal fort

Candidats — domaines à examiner

À partir des observations (et de contributions communauté), une file de domaines candidats — mirrors, TLDs, clean-brands — sans promotion automatique.

  • Sources : observations locales + seed communauté
  • Pas encore dans rules.json ni la sync distante
  • Dédup / familles (missav*, FC2, doujin markets…)

Promote — liste remote / sync

Les candidats retenus rejoignent la liste distante (desktop / Supabase / fichier ~/.clarity) — complément des règles embarquées, pas un remplacement.

  • Liste qui grandit : communauté + candidats observés
  • Mise à jour sans republier l’extension
  • Canal existant : native host / GET_CONFIG

Éval — porte avant ship

Rien ne part en prod sans passer le corpus : vrais positifs et négatifs difficiles. L’éval est une porte, pas un dashboard cosmétique.

  • Labels : block / allow / borderline + couche attendue
  • Hard negatives : éducation, médical, art, lingerie retail, Wikipedia
  • Précision / rappel — pas seulement « ça bloque missav »

Deploy — extension

Sync → DNR dynamique / blocklist adulte côté extension. Puis on observe à nouveau : la boucle se referme.

  • Couverture large sans hardcode-only
  • Chaque deploy est gaté par l’éval
  • Retour à Observe : nouveaux mirrors, nouveaux candidats

Priorités visibles — dans cet ordre :

  1. 1 Signaux structurels avant langues / keywords — la boucle observe la forme, pas le dictionnaire.
  2. 2 Liste auto-croissante — communauté + candidats observés, sync remote.
  3. 3 Éval comme porte — aucun promote/deploy sans corpus (y compris hard negatives).
  4. 4 DNS / friction anti-désactivation — hosts macOS + disable-friction v1 (délai + DISABLE) ; vault PIN plus tard.
  5. 5 Classifieur — seulement après (S4), sur features déjà là ; pas avant la boucle.
